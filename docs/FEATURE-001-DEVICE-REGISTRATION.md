# Feature 001 — Device Registration and Identity Management

**Status:** Implemented for the current development scope; production security remains deferred  
**Module:** Households and Devices  
**First hardware target:** ESP32

## Confirmed product decisions

- Only a Household Administrator may register, edit or deactivate devices. Enforcement is deferred until authentication and authorization are implemented.
- Household identifiers are generated by the backend: `H001`, `H002`, and so on.
- Device identifiers are generated by the backend in the format `H001-DEV001`.
- Device numbers are sequential within a household and are not supplied by the registering user.
- Device codes are immutable and globally unique. Deactivation does not release an identifier for reuse.
- Registration metadata: device name, hardware model, firmware version, installation location, electrical configuration (single-phase or three-phase), and optional description.
- Initial threshold settings: minimum/maximum voltage, maximum current, maximum instantaneous power, maximum daily energy, and optional maximum temperature.
- The initial threshold model has one level. A warning is raised only after a configured limit remains violated for a configurable duration.
- Thresholds are dashboard warning settings, not electrical protection settings. Local firmware protection remains separate and authoritative.

## Initial API surface

- `POST /api/households` — create a household; identifier is generated.
- `GET /api/households` — list households.
- `GET /api/households/{householdId}` — retrieve a household by its generated identifier.
- `POST /api/devices/{householdId}` — register a device and generate its device code.
- `GET /api/devices?householdId={id}&page=1&pageSize=50` — list devices, optionally filtered by household and paginated. Page sizes are limited to 100; pagination metadata is returned in `X-Total-Count`, `X-Page`, `X-Page-Size` and `X-Total-Pages` headers.
- `GET /api/devices/{deviceCode}` — retrieve a device.
- `PATCH /api/devices/{deviceCode}/deactivate` — deactivate a device.

The API currently has no authentication or role enforcement because authentication was explicitly deferred. Consequently, the administrator-only rule is a product requirement, not an enforced security boundary in this increment. Do not expose these endpoints to an untrusted network or production internet. Add authentication and authorization before production use.

## Deliberate limitations

- This increment does not implement telemetry ingestion, device authentication, automatic discovery, hardware control, local protection, threshold evaluation or notifications.
- Threshold values are optional and no electrical defaults are assumed.
- A threshold persistence duration is optional until threshold evaluation is enabled; when supplied it must be positive.
- Last-seen is a domain field only; no heartbeat endpoint updates it yet.
- Database schema creation/migrations and automated tests are included.
- Sequential allocation uses an atomic PostgreSQL `UPDATE ... RETURNING` against the household row inside the same transaction as the device insert. The row update serializes allocations for that household; this is not a transaction configured at serializable isolation. PostgreSQL concurrent-registration integration tests cover twenty simultaneous registrations, sequential unique identifiers and non-reuse after deactivation.
- No database is created automatically at application startup.
