# TELEMETRY-001 — Versioned device telemetry

## Status

The server-side schema-v1 ingestion and history query paths are implemented. The ESP32 Arduino client now includes PZEM acquisition, HTTPS provisioning, signed publishing and a bounded persistent queue. Physical PZEM hardware, calibration, production proxy behavior and end-to-end commissioning remain unverified.

## Schema v1

A telemetry envelope contains:
- schemaVersion: currently 1.
- sampleId: non-empty UUID used for per-device de-duplication.
- capturedAtUtc: UTC timestamp generated by the device.
- measurements: root aggregate values such as voltage, current, active power, energy, frequency, power factor and temperature.
- phases: optional L1/L2/L3 measurement objects.
- sensors: optional bounded dictionary of additional scalar readings.

Example:

```json
{
  "schemaVersion": 1,
  "sampleId": "f5d3f540-8a0d-4d3c-8c90-3a20e9c81020",
  "capturedAtUtc": "2026-11-07T10:15:30Z",
  "measurements": {
    "voltageVolts": 231.4,
    "currentAmps": 4.2,
    "activePowerWatts": 920.0,
    "energyWattHours": 12540.0,
    "frequencyHertz": 50.0,
    "powerFactor": 0.95
  },
  "phases": {
    "L1": {
      "voltageVolts": 231.4,
      "currentAmps": 4.2,
      "activePowerWatts": 920.0,
      "energyWattHours": 12540.0,
      "powerFactor": 0.95
    }
  },
  "sensors": {
    "boardTemperatureCelsius": 34.5
  }
}
```

Root measurements represent the primary installation reading. Phase values are optional and support future three-phase acquisition. Additional sensors are optional and bounded. At least one root or phase measurement is required.

## Authentication

POST /api/device-telemetry uses the device HMAC authentication pipeline. Headers:
- X-EMS-Device
- X-EMS-Timestamp
- X-EMS-Nonce
- X-EMS-Signature

The HMAC-SHA-256 canonical input binds method, exact path/query, timestamp, nonce and SHA-256 body digest. Device state, credential status, timestamp freshness and nonce uniqueness are validated. Device requests are rate-limited. The firmware requires a valid NTP clock and trusted root CA; it does not disable TLS validation.

## Validation and persistence

- Only schema version 1 is accepted.
- Capture time must be UTC and within seven days in the past or two minutes in the future.
- Numeric fields have configured sanity bounds; these are API input validation, not protection limits.
- At most three phase keys are accepted and they must be L1, L2 or L3.
- Additional sensors are limited to 16 entries with bounded names and numeric values.
- PostgreSQL stores the full envelope as JSONB, plus device ID, sample ID, capture time, receipt time and schema version.
- Device/sample uniqueness rejects duplicate samples.
- Server receipt time is stored separately from device capture time.

## Endpoints

| Method | Route | Description |
|---|---|---|
| POST | /api/device-telemetry | HMAC-authenticated schema-v1 publish; 202 when persisted. |
| GET | /api/devices/{deviceCode}/telemetry?fromUtc=...&toUtc=...&limit=200 | Signed-in household member reads bounded history for an accessible device. |

History query windows are UTC, ordered and at most 31 days; result limit is bounded to 500.

## Firmware queue and retry

The ESP32 stores up to eight complete payloads in Preferences/NVS. Original sample IDs and capture timestamps are retained; retries create fresh HMAC request timestamps and nonces. A duplicate response (409) is treated as already delivered. Queue overflow retains existing samples and rejects the newest. Permanently invalid payloads are removed so they cannot block later entries. This queue covers short outages only, not long-term archival.

## Dashboard semantics

The dashboard uses the latest stored sample per device:
- Total active power is the sum of available per-device active-power readings.
- Voltage and current are averages of available per-device readings.
- Cumulative energy is the sum of available cumulative meter counters.
- Missing values remain unavailable rather than becoming zero.
- Cumulative energy is not a daily-energy calculation.
- A stored sample / last receipt timestamp is not a definitive online/offline state.

## Safety boundary

Telemetry validation and dashboard thresholds are not electrical protection. No relay/contactor command or protective trip is driven by telemetry ingestion. Local safety and certified electrical protection remain independent.
